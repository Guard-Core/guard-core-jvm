    W8b release rehearsal (2026-10-11)

NOTHING was published to any remote registry, no tags were created, no publish workflow runs were triggered: every publish here went to mavenLocal and every registry touch was a read-only GET. The first real upload happens only on operator go, through docs/release.md.

    2. Auth-path decision and what is pending (operator)

    Verified (2026-10-11, central.sonatype.org Publisher API docs + release notes):

    • The Central Portal Publisher API authenticates with a Portal user token (Authorization: Bearer base64(username:password)). The workflows are built for this path via four secrets: CENTRAL_PORTAL_USERNAME, CENTRAL_PORTAL_PASSWORD, GPG_PRIVATE_KEY, GPG_PASSPHRASE.
    • OIDC trusted publishing does not exist for Maven Central (npm/PyPI/ Packagist have it; Maven does not). Therefore the publish jobs carry contents: read only and no id-token scope. If Sonatype ships trusted publishing, that is a follow-up, not a blocker.
    • GPG signing is mandatory (every file needs .asc; proven in 1.5).
    • New publishing limits took effect 2026-10-01 (announced 2026-06-16, enforcement pushed from Aug 11; 30-day grace): three monthly per-org metrics (file count, release size, release count), Usage Center is the source of truth. This family is orders of magnitude below the thresholds.

    Pending on the operator (each blocks the corresponding step of docs/release.md):

    1. Portal user token generated and the two CENTRAL_PORTAL_* secrets set on all four repos. Blocks: the publish jobs' credential gate.
    2. GPG key pair created, the public key uploaded to a keyserver (the Portal validates against the keyserver copy), and the armored secret key + passphrase set as GPG_PRIVATE_KEY / GPG_PASSPHRASE on all four repos (4 secrets per repo in total, counting the two Portal ones). Blocks: the publish jobs' GPG gate (and Portal validation).
    3. GitHub releases created per tag at train time (the publish jobs fire on release: created, not on the tag push alone). Blocks: publishing only.

    RESOLVED (was pending item 1): the Portal namespace com.guard-core flipped to VERIFIED 2026-10-11 16:15 (Portal badge, Org Guard-core). History: com.guardcore was abandoned 2026-10-11 (guardcore.com is a parked domain the operator does not own, making that claim unverifiable); com.guard-core reverses to the owned guard-core.com; the operator re-registered, swapped the apex TXT to the new verification key, and the Portal validated it.

    3. Remaining operator steps (release day, condensed)

    The full choreography is docs/release.md; the condensed checklist:

    1. Confirm the Portal shows com.guard-core Verified; secrets set on all four repos (section 2 items 1-2); Usage Center clean.
    2. Engine: tag v4.3.2 on a green master -> gates green -> create the GitHub release -> publish job uploads + VALIDATES both deployments (engine first, facade second) -> click Release on both in the Portal UI -> repo1 answers 200 for both artifacts.
    3. Adapters + agent, in any order (each guarded by its own pre-flight): version-flip PR merged (1.0.0-SNAPSHOT -> 1.0.0, 3.2.2-SNAPSHOT -> 3.2.2; CHANGELOG ## [SEMVER] - YYYY-MM-DD) -> tag -> release created -> pre-flight proves the engine live -> publish -> Portal release -> repo1 200.
    4. Post-release audits (per tag): GitHub release page exists; repo1 200 per artifact; no deployment left VALIDATED/PENDING in the Portal; Usage Center clean. Then move the consumers' pinned engine refs to the released engine SHA in the next regular development PR.

    Rollback: before the Portal click, Drop the deployment (nothing published); after the click there is no undo - only a fix version (artifacts are immutable; tags of published versions never get deleted).
