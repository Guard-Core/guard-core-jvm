    Route-id collision study (the guard-core #141/#142 class): the python bug was factory-built endpoints (closures sharing one __qualname__) deriving the same module.qualname route id, so one endpoint could select another's RouteConfig; python's defense (decorators/base.py:84-105) reuses a stamped id only when the SAME instance assigned it to the SAME function object (owner chain over id(func)/__wrapped__), else allocates key#2.

    JVM capability comparison: route identity is caller-supplied object identity (StampedRoute carrying stampedRouteId, or a string key) - the analog of the TS WeakMap case. Two factory-built endpoints in the JVM are two distinct StampedRoute objects, so the derived-key collision class python had cannot occur: identical base keys get key#2-style suffixes per instance, and stamped ids are never reused across instances (the owner map). SecurityDecoratorTest (route-id collision campaign) ports tests/test_decorators/test_route_id_per_function.py 1:1: own-rate-limit isolation, settings not leaking, first endpoint keeps the plain key, stacked decorators share one config (the intentional case), and cross-instance stamped-id non-reuse.

    Java bridges

    guard-core/src/main/kotlin/com/guardcore/java/JavaBridges.kt - the convention: every public async entry point ships three shapes (suspend for Kotlin, blocking static = runBlocking confined to the entry point (the unasync analog per specs/impl/jvm.md), future static = CompletableFuture over the IO dispatcher):

    • pipeline run: executePipeline / executePipelineBlocking
    • detection: detect / detectBlocking (SusPatternsManager.detect)
    • handlers: banIp, unbanIp, checkRateLimit (adapter supplies the error factory), getSecurityHeaders, initializeRedis, applyBehaviorAction (+ blocking pairs)

    Proven from Java source in guard-core/src/test/java/com/guardcore/java/JavaBridgeConsumerTest.java.
